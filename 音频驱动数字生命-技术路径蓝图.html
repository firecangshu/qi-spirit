音频驱动数字生命 · 技术路径蓝图

一套「输入任意音频 → 驱动数字生物自主演化的可插拔视觉系统」技术方案。无指令时自主运行四种本能行为，有音频时随节拍、音量、频段实时响应。视觉皮肤可切换（流体金属 / 蜂群粒子 / 半透明胶质 / 机械细胞），底层逻辑与架构完全复用。

逻辑层面 · 状态机 构架层面 · 四层解耦 调用层面 · 接口协议 技术栈 · Web / TD / UE

总览：三层面一图看懂

逻辑层面回答「它怎么决策」，构架层面回答「系统怎么分层」，调用层面回答「代码怎么衔接」。三者通过一份标准运动参数协议贯通。

层面回答的问题核心产物
逻辑层面生物如何决策：何时自主、何时响应音频、如何过渡行为状态机、音频特征映射规则、过渡/限幅策略
构架层面系统如何分层：哪些模块、各自职责、如何解耦四层架构、层间数据协议、技术栈选型
调用层面代码如何衔接：谁调用谁、传什么、什么顺序接口签名、主循环时序、最小可运行骨架

系统全景架构 · 依赖关系与分层

完整系统从「输入 → 前端 → 后端 → 方法层 → 工具层 → 执行器」逐层依赖。执行器层预留硬件终端接口：当前以 3D 视频展示为默认执行器，未来可无缝切换为机械模块驱动的真实「炁灵实体」，行为逻辑与上层完全不变。

0.2 执行器抽象：一个接口，双输出（炁灵可虚拟可实体）

关键设计：行为引擎不直接产画面，也不直接驱机械，只输出统一的「动作指令流」。渲染层和硬件层各自实现一个执行器适配器来消费同一份指令——这就是"3D 视频"与"机械实体"能无缝切换的根本原因。

  • 执行器B · 硬件终端（预留）：同一份动作指令经协议转换 → 驱动机械模块（如点阵像素块、舵机阵列、震动单元），构建物理世界的炁灵实体。

0.3 炁灵动作指令协议（连接虚拟与实体的桥）

行为引擎输出的这份指令，既驱动 3D 渲染，也可翻译成硬件时序，是「虚拟 ↔ 实体」统一的契约：

// QilingCommand —— 炁灵统一动作指令（执行器无关）
{
  "id":         "qiling-01",
  "state":      "breath | flow | vibrate | swim | audio",
  "tick":       0.016,          // 帧间隔秒
  "motion": {
    "intensity": 0.0–1.0,       // 整体强度
    "flowSpeed": 0.0–1.0,       // 流动速度
    "pulse":     0.0–1.0,       // 脉冲幅度
    "tremor":    0.0–1.0,       // 震颤强度
    "direction": [x, y, z],     // 方向
    "scale":     0.5–1.5,       // 缩放
    "active":    0.0–1.0        // 活跃度
  },
  "origin":     "audio | autonomous"  // 触发来源
}
硬件映射示意（预留方向）：机械模块可采用「像素块点阵」方案——每个像素块是一个由舵机/电机驱动的活动单元。将 3D 粒子数据的密度场投影到 2D 点阵，`intensity`→推动高度，`pulse`→时序脉冲，`tremor`→高频振动频率。这样同一个炁灵，既能以 3D 视频呈现，也能以实体点阵再现。

第一部分 · 逻辑层面（Behavior Logic）

核心思想：一套「自主本能 + 外部响应」双模式状态机。无音频时自主循环，有音频时进入响应态，二者用平滑过渡衔接，避免机械感。

1.1 双模式总览

模式A · 自主本能无音频/音量低于阈值
⟷
模式B · 音频响应检测到有效音频
  • 模式A：运行「呼吸 → 流动 → 震动 → 游弋」四状态随机循环，权重与时长随机化，模拟生命节律。
  • 模式B：解析音频特征（节拍/分频段能量/音量），映射为运动参数驱动同一套粒子系统。
  • 切换：音频进入用 1–2s 交叉淡入；音频结束用 3–5s 余韵衰减回退，不允许硬切。

1.2 自主状态机（四标准剧本）

呼吸 BREATHING基础态 · 正弦缩放 0.2–0.4Hz 流动 FLOWING内部定向循环 · 10–20s 震动 VIBRATING高频微颤 8–15Hz · 3–8s 游弋 SWIMMING整体位移 · 15–30s
状态核心运动逻辑（框架层）典型视觉（渲染层）状态权重
呼吸整体周期正弦缩放，中心密度高低交替，粒子径向小幅位移流体版：表面平缓起伏；蜂群版：整体聚散40%（基础态，最高）
流动粒子沿某轴向定向循环，整体缓慢形变，不发生位移表面连续波纹扫过；粒子群内部环流30%
震动高频小幅抖动，轮廓不变，内部粒子速度提升（蓄力/警觉）表面高频细碎波纹；粒子个体快速震颤10%
游弋整体沿平滑路径移动，形态自适应拉长为流线型流体版水滴形前移；蜂群版集群漂移20%
状态衔接三规则：① 呼吸是基础态，其余状态从呼吸切入、也回到呼吸；② 所有切换用 1–3s 线性插值过渡（如呼吸→流动：先加速内部粒子，再出现定向流）；③ 按权重随机调度下一个状态，保证整体偏平静、偶尔活跃，像真实生物节律。

1.3 音频特征提取（输入标准化）

任意音源（音乐 / 人声 / 现场声 / 钢琴MIDI）统一提取三个维度：

特征检测方式含义 / 用途
节拍 / 重拍 Onset能量突变峰值检测「什么时候动一下」→ 触发径向冲击波
分频段能量FFT 频谱分离（Bass / Mid / Treble）「哪里怎么动」→ 低频驱整体、中频驱流动、高频驱震颤
整体音量 RMS短时能量均方根 + 平滑滤波「动多大」→ 映射运动幅度与亮度
关键坑：普通 FFT 有 100–300ms 延迟，快节奏会对不上拍。解决：用 onset 检测 + 频段分离（低音专做鼓点检测，中高音做音符 onset），不要用全局能量一刀切。若对接钢琴机器人，直接用 MIDI 信号驱动，零延迟、精度 100%。

1.4 音频特征 → 运动参数映射表

音频特征映射到运动（驱动粒子仿真层）
重拍 / Onset一次径向冲击波脉冲，从中心（或发声点）向外扩散波纹
低频 Bass整体级收缩 / 大脉冲（呼吸的强化版）
中频 Mid内部粒子流动速度、表面波纹密度
高频 Treble高频震颤、边缘粒子活跃度（震动的强化版）
音量 RMS ↑粒子速度更快、脉冲幅度更大、整体亮度更高

1.5 三条防机械感逻辑（生命感关键）

  1. 交叉过渡：自主 ↔ 响应用权重淡入淡出（2s 内自主权重降至 20%，响应升至 80%），音频结束 3–5s 衰减回退。
  2. 动态限幅：音量超过阈值后运动幅度增量递减（压缩），保证大音量时粒子不飞散、轮廓不破碎；能量越大内部流动越快，而非整体炸开。
  3. 微扰动：所有响应参数上叠加一层低频随机噪声（幅度很小），制造「呼吸感」与「不完美感」——这是区分「音乐可视化」与「数字生命」的分水岭。

第二部分 · 构架层面（System Architecture）

核心原则：四层严格解耦，层间只通过标准参数协议通信，绝不互相调用内部。换视觉皮肤、加新输入源、切换输出端（3D/硬件）都只改对应一层。注意：此处的「四层」指运行时的数据管道（输入→行为→仿真→渲染），是全景六层中方法层与前端的具体化。

① 输入层把任意音源标准化为特征音频流 → {beat, rms, bass, mid, treble}Web Audio API + FFT；MIDI 用 Web MIDI API
② 行为层决策：状态机 + 映射 + 过渡特征 + 时间 → 运动参数 MotionParams纯 JS 状态机模块（后端方法层）
③ 仿真层通用粒子物理计算MotionParams → 粒子位置/速度/密度Three.js + GPU 粒子 / 自定义 shader
④ 渲染/输出层把粒子数据呈现为画面或指令粒子数据 → 屏幕画面 或 执行器指令GLSL 着色器（四皮肤）+ 执行器适配器
为什么能「换皮不换骨」：流体 = 粒子密度场提取连续表面（Marching Cubes）；蜂群 = 每个粒子单独渲染；胶质 = 半透明包膜 + 内部微光；机械细胞 = 粒子替换为微型单元模型。四种皮肤共用同一套仿真数据，只改第④层。同理，把第④层换成「执行器适配器」，即可输出给硬件机械模块。

2.2 层间数据协议（标准运动参数）

这是四层解耦的「契约」，所有层都读写这份结构：

// MotionParams —— 层间通用协议
{
  "mode":    "breath | flow | vibrate | swim | audio",  // 当前行为模式
  "intensity": 0.0–1.0,   // 整体强度（音量映射）
  "flowSpeed": 0.0–1.0,   // 流动速度（中频映射）
  "pulse":     0.0–1.0,   // 脉冲幅度（重拍/低频映射）
  "tremor":    0.0–1.0,   // 震颤强度（高频映射）
  "direction": [x, y, z], // 行为方向（游弋/流动轴向）
  "scale":     0.5–1.5,   // 整体缩放（呼吸/游弋形态）
  "active":    0.0–1.0    // 活跃度（限幅后的能量）
}

第三部分 · 调用层面（Invocation / API）

明确四层各自的对外接口、主循环时序，以及一份可落地的调用骨架。

3.1 主循环时序（每帧执行顺序）

初始化
  audioEngine.init(音频源)        // 输入层
  behaviorEngine.reset()          // 行为层
  simEngine.init(粒子数)          // 仿真层
  renderEngine.setSkin("gel")     // 渲染层选皮肤

每帧 update(dt)
  1. features = audioEngine.getFeatures()          // 输入层：解析音频
  2. motion   = behaviorEngine.update(features, dt)// 行为层：状态机+映射
  3. simEngine.setParams(motion); simEngine.update(dt) // 仿真层：物理计算
  4. renderEngine.render(simEngine.getParticles()) // 渲染层：绘制

3.2 四层接口签名

① 输入层 AudioEngine

  • init(source) 装载音频/MIDI源
  • getFeatures() → {beat, rms, bass, mid, treble}
  • onBeat(cb) 重拍回调（冲击波触发）
  • getLatency() 延迟探测

② 行为层 BehaviorEngine

  • update(features, dt) → MotionParams
  • setState(mode) 手动切状态
  • onStateChange(cb) 状态变更回调
  • 内部：自主状态机 + 映射 + 过渡

③ 仿真层 SimulationEngine

  • init(count) 粒子数
  • setParams(motion) 注入运动参数
  • update(dt) 物理步进
  • getParticles() → Float32Array 位置数据

④ 渲染层 RenderEngine

  • setSkin("liquid|swarm|gel|mech")
  • render(particleData) 绘制帧
  • setUniforms({...}) 材质微调

3.3 执行器接口（3D 视频 ↔ 硬件终端 双输出切换）

后端输出统一的 QilingCommand，由执行器层按需选择消费方——当前接 3D 渲染器，未来接硬件驱动，调用面完全一致。

// 统一指令输出接口（后端 → 执行器层）
class QilingExecutor {
  // 执行器A：3D 视频展示（默认，无实体时使用）
  render3D(command)  { /* 粒子仿真 + GLSL 渲染 + 可录屏 */ }

  // 执行器B：硬件终端（预留接口，未来接机械模块）
  // 约定协议：JSON over WebSocket / 串口
  driveHardware(command) {
    // command.motion.intensity -> 推动高度
    // command.motion.pulse    -> 时序脉冲
    // command.motion.tremor   -> 高频振动频率
    // 投影为 2D 点阵像素块 / 舵机阵列控制信号
  }

  // 执行器注册表：运行时选择目标
  setTarget("3d" | "hardware");
}
切换方式：行为引擎与仿真层不变，仅通过 executor.setTarget() 决定输出到 3D 渲染还是硬件。当前阶段保持 "3d"，用 3D 视频展示炁灵实体；硬件模块到位后切换为 "hardware" 即完成实体化，逻辑零改动。

3.4 最小可运行调用骨架（伪代码）

const audio   = new AudioEngine();
const brain   = new BehaviorEngine();   // 含4自主态 + 音频映射
const sim     = new SimulationEngine();
const render  = new RenderEngine();

function setup(){
  audio.init(loadAudio("sample.mp3"));
  render.setSkin("liquid");   // 可切换 swarm / gel / mech
  sim.init(60000);            // 6万粒子起步
  brain.onStateChange(s => log("生物进入：" + s));
}

function animate(dt){
  const f = audio.getFeatures();            // ① 听觉
  const m = brain.update(f, dt);            // ② 决策
  sim.setParams(m); sim.update(dt);         // ③ 身体
  render.render(sim.getParticles());        // ④ 皮肤
  requestAnimationFrame(() => animate(dt));
}
setup();
animate(0.016);

注：骨架仅示意调用关系与数据流向，具体库 API 以所选技术栈为准。
